# Справочник сотрудников организации

Техническое задание и контекст для реализации в OpenCode.

## 1. Правила работы над проектом

Разрабатывать приложение последовательно. Перед переходом к следующему этапу:

1. Кратко объяснить, что будет сделано и зачем.
2. Показать создаваемые или изменяемые файлы.
3. Объяснить значимые строки Ruby, Rails, Slim, JavaScript, Dockerfile и YAML.
4. Выполнить относящиеся к этапу тесты и линтеры.
5. Сообщить результат проверки.
6. Получить подтверждение пользователя перед следующим крупным этапом.

Не менять выбранный стек без предварительного согласования. Не добавлять гемы «на всякий случай». Сохранять простую Rails-архитектуру, пока усложнение не станет обоснованным.

Не удалять и не перезаписывать пользовательские изменения. Не выполнять разрушительные Git-команды. Не помещать секреты, рабочую базу данных и `config/master.key` в Git.

Каждый значимый этап оформлять отдельным тематическим Git-коммитом.

## 2. Назначение приложения

Создать веб-приложение «Справочник сотрудников организации».

Сотрудник одновременно является пользователем системы. Отдельной модели `Employee` и отдельной модели `Profile` не будет: используется единая модель `User`.

Регистрация пользователей отсутствует. Сотрудников создаёт администратор. Любая страница приложения доступна только после аутентификации.

## 4. Создание приложения

Rails должен использовать строго выбранные версии Ruby и Rails. Перед `rails new` проверить:

~~~bash
ruby -v
rails -v
~~~

Создать приложение с Importmap и Bootstrap через cssbundling-rails. SQLite является базой по умолчанию. Не отключать Git и Docker-файлы, генерируемые Rails.

Зафиксировать версию Ruby в `.ruby-version`. Сохранять `Gemfile.lock` и `yarn.lock` в Git.

Сразу после создания приложения подключить:

~~~ruby
gem "slim-rails"
gem "blueprint-html2slim", "~> 1.3.1", group: :development
~~~

Начальные ERB-шаблоны преобразовать через команду `html2slim` из гема `blueprint-html2slim`, проверить результат и удалить заменённые ERB-файлы. Все новые представления писать на Slim. `blueprint-html2slim` нужен как одноразовый инструмент преобразования в development-группе, а не как часть приложения во время выполнения. Он заменяет несовместимый с Ruby 4.0.6 гем `html2slim`, который использует удалённый метод `File.exists?`.

## 5. Модель Position

Таблица `positions`:

| Поле | Тип | Ограничения |
|---|---|---|
| name | string | обязательно, уникально |
| created_at | datetime | Rails |
| updated_at | datetime | Rails |

Модель:

~~~ruby
class Position < ApplicationRecord
  has_many :users,
           inverse_of: :position,
           dependent: :restrict_with_error

  validates :name, presence: true, uniqueness: true
end
~~~

Добавить уникальный индекс базы данных на `positions.name`. `restrict_with_error` должен запрещать удаление должности, назначенной хотя бы одному пользователю.

Начальные значения:

- должность 1;
- должность 2;
- должность 3.

Интерфейс CRUD для должностей в первоначальный объём работ не входит.

## 6. Модель User

Таблица `users`:

| Поле | Тип | Ограничения |
|---|---|---|
| last_name | string | обязательно |
| first_name | string | обязательно |
| middle_name | string | необязательно |
| position_id | foreign key | обязательно |
| hired_on | date | обязательно |
| phone | string | необязательно |
| email | string | необязательно |
| login | string | обязательно, уникально без учёта регистра |
| encrypted_password | string | обязательное поле Devise |
| created_at | datetime | Rails |
| updated_at | datetime | Rails |

Не создавать столбец `password`. `password` и `password_confirmation` — виртуальные атрибуты Devise. В базе хранится только необратимый хеш в `encrypted_password`.

Связь:

~~~ruby
class User < ApplicationRecord
  belongs_to :position, inverse_of: :users
end
~~~

Базовые проверки:

~~~ruby
validates :last_name, :first_name, :hired_on, :login, presence: true
validates :login, uniqueness: { case_sensitive: false }
~~~

Добавить уникальный индекс базы данных на нормализованный логин с учётом возможностей SQLite. Перед валидацией и сохранением логин приводить к согласованному виду, как минимум удалять пробелы по краям и приводить к нижнему регистру.

Метод ФИО:

~~~ruby
def full_name
  [last_name, first_name, middle_name].compact_blank.join(" ")
end
~~~

## 7. Devise

Настроить аутентификацию по `login`, а не по email.

Регистрация отключена:

~~~ruby
devise_for :users, skip: [:registrations]
~~~

Все контроллеры по умолчанию требуют вход:

~~~ruby
before_action :authenticate_user!
~~~

Email остаётся необязательным. Если используется модуль `validatable`, корректно переопределить требование email либо оставить только нужные проверки так, чтобы пустой email был допустим, а заполненный проверялся на формат.

Самостоятельное восстановление пароля по email в первоначальную версию не входит.

## 8. Rolify

Использовать Rolify и его таблицы `roles` и `users_roles`.

Доступные роли:

- `admin`;
- `employee`.

У каждого пользователя должна быть ровно одна из этих ролей. Роль не хранить строковым полем в таблице `users`.

Примеры:

~~~ruby
user.add_role(:admin)
user.add_role(:employee)
~~~

Создание пользователя и назначение роли выполнять атомарно:

~~~ruby
User.transaction do
  user = User.create!(attributes)
  user.add_role(role)
  user
end
~~~

Если сохранение пользователя или назначение роли завершилось ошибкой, вся транзакция должна откатиться. Аналогично обновлять данные и роль администратора.

## 9. Pundit и матрица прав

Подключить Pundit. Авторизация должна проверяться на сервере. Недостаточно просто спрятать кнопку во view.

| Действие | Администратор | Сотрудник |
|---|---:|---:|
| Вход в систему | Да | Да |
| Просмотр реестра | Да | Да |
| Просмотр карточки сотрудника | Да | Да |
| Просмотр телефона и email | Да | Да |
| Просмотр логинов | Да | Нет |
| Просмотр ролей | Да | Нет |
| Просмотр паролей | Нет | Нет |
| Создание сотрудников | Да | Нет |
| Редактирование любого сотрудника | Да | Нет |
| Удаление сотрудников | Да | Нет |
| Изменение роли | Да | Нет |
| Изменение собственного телефона | Да | Да |
| Изменение собственного email | Да | Да |
| Изменение собственного логина | Да | Да |
| Изменение собственного пароля | Да | Да |
| Выгрузка XLSX | Да | Да |
| Просмотр аналитики | Да | Нет |

Пароль нельзя показать даже администратору. Администратор может только установить пользователю новый пароль.

При реализации отдельно защититься от ситуации, когда система остаётся без единственного администратора. Конкретное правило удаления последнего администратора согласовать с пользователем перед реализацией.

## 10. Общий реестр

Общие маршруты:

~~~ruby
resources :users, only: %i[index show]
~~~

Реестр доступен всем аутентифицированным пользователям.

Обычный сотрудник видит:

- ФИО;
- должность;
- дату приёма;
- телефон;
- email.

Администратор дополнительно видит:

- логин;
- роль;
- действия редактирования и удаления.

Не передавать закрытые административные поля в пользовательские JSON/API-ответы, если такие ответы появятся. Пароль и `encrypted_password` не выводить нигде.

## 11. Административный CRUD

Маршруты:

~~~ruby
namespace :admin do
  resources :users
  resource :analytics, only: :show
end
~~~

Администратор может устанавливать и изменять:

- фамилию;
- имя;
- отчество;
- должность;
- дату приёма;
- телефон;
- email;
- логин;
- пароль;
- роль.

Для административного создания и обновления использовать отдельные strong parameters. Не передавать имя роли напрямую в `User.new` или `User.update`: назначать её через Rolify внутри транзакции.

Пустой пароль при редактировании существующего пользователя означает «не менять пароль».

## 12. Личный профиль

Отдельную модель `Profile` не создавать. Профиль — отдельный ресурс и контроллер, изменяющий текущий `User`:

~~~ruby
resource :profile, only: %i[edit update]
~~~

~~~ruby
class ProfileController < ApplicationController
  def edit
    @user = current_user
  end

  def update
    @user = current_user
  end
end
~~~

Профиль доступен сотруднику и администратору. Разрешённые поля:

- `phone`;
- `email`;
- `login`;
- `password`;
- `password_confirmation`;
- при необходимости `current_password` для безопасной смены учётных данных.

Никогда не загружать пользователя профиля по `params[:id]`. Всегда использовать `current_user`.

## 14. Аналитика

Страница:

~~~text
/admin/analytics
~~~

Доступна только администратору и защищена `AnalyticsPolicy`.

Вывести:

- все должности, включая должности без сотрудников;
- общее число сотрудников по каждой должности;
- пять последних принятых сотрудников по каждой должности;
- ФИО;
- дату приёма;
- ссылку на карточку сотрудника.

Сортировать по дате приёма, а не по времени создания записи:

~~~ruby
position.users.order(hired_on: :desc, id: :desc).limit(5)
~~~

`id: :desc` обеспечивает устойчивый порядок для сотрудников с одинаковой датой приёма.

Вначале допустима простая читаемая реализация с отдельным запросом для каждой из трёх должностей. После получения работающего варианта проверить SQL в логах. Оптимизировать оконной функцией или другим запросом только при реальной необходимости.

## 15. Представления и формы

Использовать Slim и Simple Form:

~~~ruby
gem "simple_form", "~> 5.4"
~~~

Установка:

~~~bash
bin/rails generate simple_form:install --bootstrap
~~~

Пример административной формы:

~~~slim
= simple_form_for [:admin, user] do |f|
  = f.input :last_name
  = f.input :first_name
  = f.input :middle_name
  = f.association :position,
                  collection: Position.order(:name),
                  include_blank: false
  = f.input :hired_on, as: :date, html5: true
  = f.input :phone
  = f.input :email
  = f.input :login
  = f.input :password,
            required: user.new_record?,
            hint: user.persisted? ? "Оставьте пустым, чтобы не менять пароль" : nil
  = f.input :password_confirmation
  = f.button :submit, class: "btn btn-primary"
~~~

Simple Form строит HTML и показывает ошибки, но не заменяет проверки модели.

## 16. Frontend

Использовать:

- Bootstrap 5;
- SCSS;
- адаптивные таблицы;
- flash-сообщения;
- Turbo Drive;
- Stimulus для небольшой интерактивности;
- Importmap для JavaScript-модулей;
- Propshaft для ассетов.

Не использовать Turbolinks: его современная замена — Turbo. Не использовать rails-ujs: подтверждения и HTTP-действия реализовывать средствами Turbo и Rails helpers, например `button_to`.

Node.js и Yarn используются для сборки Bootstrap SCSS через cssbundling-rails:

~~~text
app/assets/stylesheets/application.bootstrap.scss
                       |
                       v
                yarn build:css
                       |
                       v
app/assets/builds/application.css
~~~

В разработке запускать:

~~~bash
bin/dev
~~~

Importmap не выполняет сборку приложения в браузере. Он сообщает браузеру, по какому URL находится модуль с указанным логическим именем. Локальные загруженные JavaScript-файлы могут находиться в `vendor/javascript`.

При добавлении Stimulus-контроллеров объяснять:

- `export default class extends Controller`;
- что означает `this`;
- как `static targets = ["input"]` создаёт `this.inputTarget`, `this.inputTargets` и `this.hasInputTarget`;
- DOM, свойства элементов, обработчики событий и `fetch`.

## 17. Начальные данные

`db/seeds.rb` должен идемпотентно создавать три должности и первоначального администратора.

Данные администратора:

| Поле | Значение |
|---|---|
| last_name | Администратор |
| first_name | Системы |
| middle_name | пусто |
| position | должность 1 |
| hired_on | текущая дата при первом создании |
| login | значение `ADMIN_LOGIN` или `admin` |

Учетные данные `admin/admin` допустимы только как условие учебного задания. В README явно указать, что для реального развёртывания пароль необходимо переопределить.

## 19. Docker

Использовать Rails production Dockerfile как основу. Адаптировать build-стадию под Node.js/Yarn и сборку SCSS.

Dockerfile должен быть многоэтапным:

1. `build` — установка гемов и JavaScript-зависимостей, сборка CSS и ассетов;
2. финальный runtime-образ — только необходимые для запуска зависимости и готовое приложение.

Основные инструкции `FROM`, `WORKDIR`, `COPY`, `RUN`, `ENV`, `ENTRYPOINT` и `CMD` объяснить при реализации.

`docker-compose.yml` содержит один Rails-сервис. Отдельный контейнер базы не нужен, поскольку используется SQLite.

Ориентир:

~~~yaml
services:
  web:
    build: .
    ports:
      - "3000:80"
    environment:
      RAILS_ENV: production
      RAILS_MASTER_KEY: ${RAILS_MASTER_KEY}
    volumes:
      - storage:/rails/storage

volumes:
  storage:
~~~

Каталог `/rails/storage` подключить как постоянный Docker volume, чтобы SQLite-база не исчезала при пересоздании контейнера.

Команды:

~~~bash
RAILS_MASTER_KEY="$(cat config/master.key)" docker compose up --build
docker compose ps
docker compose logs -f web
docker compose exec web bin/rails console
docker compose down
~~~

`docker compose down --volumes` удаляет volume и может удалить SQLite-базу. Не выполнять эту команду без осознанного подтверждения.

Обычная локальная разработка первоначально ведётся через `bin/dev`. Docker используется для проверки production-подобной сборки и запуска.

## 20. Тесты и критерии готовности

Минимально проверить:

### Модели

- обязательность полей `User` и `Position`;
- уникальность нормализованного логина;
- уникальность названия должности;
- `inverse_of` у обеих сторон связи;
- запрет удаления используемой должности;
- формирование `full_name`.

### Аутентификация

- вход по login и паролю;
- отсутствие публичной регистрации;
- перенаправление неаутентифицированного пользователя на вход;
- невозможность входа с неверным паролем.

### Авторизация

- сотрудник не открывает административные маршруты;
- сотрудник не изменяет чужую карточку;
- сотрудник меняет только разрешённые поля своего профиля;
- сотрудник не видит login и role;
- администратор выполняет CRUD пользователей;
- аналитика доступна только администратору.

### Роли и транзакции

- новый пользователь получает ровно одну роль;
- ошибка назначения роли откатывает создание;
- смена роли и изменение пользователя выполняются атомарно.

### Excel

- файл доступен обоим ролям;
- содержит только ФИО, должность, телефон и email;
- не содержит login, role и password.

### Аналитика

- отображаются должности без сотрудников;
- для каждой должности выводится не больше пяти сотрудников;
- используется сортировка по `hired_on DESC`;
- отображается правильное общее количество.

### Docker

- образ успешно собирается;
- контейнер запускается;
- миграции и seeds выполняются;
- приложение открывается на `http://localhost:3000`;
- SQLite-данные сохраняются после пересоздания контейнера без удаления volume.

Перед завершением проекта запустить полный набор:

~~~bash
bin/rails test
bin/rails test:system
bin/rubocop
bin/brakeman
~~~

Команды корректировать по реально сгенерированным binstub-файлам.
